# Deploying to Render (free) with Supabase

You will create three things: a **Supabase** project (database and file storage), a **GitHub OAuth App** (sign-in and read access), and a **Render** web service (the app). Then you add two optional GitHub Actions setups (scheduled sync and backups).

Keep every secret out of Git. They only go into the Render dashboard and GitHub repository secrets.

---

## 1. Supabase: database and storage

1. Create a free project at <https://supabase.com>. Pick a region close to you and to Render (e.g. Frankfurt / `eu-central-1`).
2. **Database URL.** Open *Connect* and copy the **Session pooler** connection string (port `5432`, host like `aws-0-eu-central-1.pooler.supabase.com`). Replace `[YOUR-PASSWORD]` with the database password.
   * Use the *session* pooler, not the direct connection (direct connections are IPv6-only, which Render may not reach) and not the *transaction* pooler (port 6543), because the app uses prepared statements.
   * The app accepts `postgresql://…` and converts it to the psycopg driver itself.
3. **Storage bucket.** Go to *Storage → New bucket*, name it `documents`, and leave **Public bucket OFF**. The app reads and writes it from the server only.
4. **Service key.** In *Project Settings → API*, copy the **project URL** and the **`service_role` key**. The service role key bypasses Supabase's row security, so it must only ever be a server environment variable. The app never sends it to the browser.

> Free Supabase projects pause after a period of inactivity (about a week). The scheduled sync (step 5) touches the database every few hours, which should keep it awake. If it does pause, restore it from the Supabase dashboard; no data is lost.

## 2. GitHub OAuth App: sign-in and read access

1. GitHub → *Settings → Developer settings → OAuth Apps → New OAuth App*.
2. Fill in:
   * **Application name:** Navigator ProjectOS
   * **Homepage URL:** `https://<your-service>.onrender.com` (you can edit it after step 3 once you know the exact name)
   * **Authorization callback URL:** `https://<your-service>.onrender.com/api/v1/auth/github/callback`
3. Create it, then **Generate a new client secret**. Copy the **Client ID** and **Client secret**.
4. Your **numeric GitHub user id**: open `https://api.github.com/users/<your-login>` and copy `"id"`. Only this id will be allowed to sign in. (If you skip this, the login page will show your id after a rejected sign-in.)

**Why an OAuth App and not a GitHub App?** GitHub Apps only get a *Projects* permission for organization-owned boards; reading **your personal Projects (v2) boards** needs the classic `read:project` OAuth scope. The app requests `read:user repo read:project`.

* `repo` is the only scope that gives read access to *private* repositories, and GitHub doesn't offer a read-only version of it. ProjectOS itself never writes: its GitHub client only performs `GET` requests and GraphQL *queries*, and it rejects any GraphQL mutation (there is a test for this).
* If all your repositories are public, set `GITHUB_OAUTH_SCOPES=read:user public_repo read:project` for narrower access.

## 3. Generate the app's own secrets

Run these on your computer (any machine with Python and the `cryptography` package):

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"                                  # SESSION_SECRET
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"     # ENCRYPTION_KEY
python -c "import secrets; print(secrets.token_urlsafe(48))"                                  # INTERNAL_SYNC_SECRET
```

`ENCRYPTION_KEY` encrypts your GitHub token in the database. If you lose or change it, just sign in with GitHub again.

## 4. Render: the web service

1. Push this repository to GitHub (already done if you're reading it there).
2. In Render: *New → Blueprint*, choose this repository. Render reads `render.yaml` and proposes one **free web service** called `navigator-projectos`.
3. Fill in the environment variables it asks for:

   | Variable | Value |
   | --- | --- |
   | `PUBLIC_BASE_URL` | `https://<your-service>.onrender.com` (no trailing slash) |
   | `DATABASE_URL` | Supabase session pooler string from step 1 |
   | `ENCRYPTION_KEY` | from step 3 |
   | `INTERNAL_SYNC_SECRET` | from step 3 |
   | `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET` | from step 2 |
   | `ALLOWED_GITHUB_USER_IDS` | your numeric GitHub id (comma-separate if you ever add more) |
   | `SUPABASE_URL` / `SUPABASE_SERVICE_KEY` | from step 1 |

   `SESSION_SECRET` is generated by Render automatically. `ENVIRONMENT=production` and `STORAGE_BACKEND=supabase` are set by the blueprint.
4. Deploy. The build runs `npm ci && npm run build` for the frontend and `pip install` for the backend; the start command runs `alembic upgrade head` and then the server. The app **refuses to start** in production if a required secret is missing or unsafe (for example if dev login is enabled). Check the Render logs if it fails.
5. Open the URL and click **Sign in with GitHub**.

### What the free plan means in practice

* After 15 minutes without traffic the service sleeps. The next visit takes about a minute; the app shows “Waking up the server…” and retries.
* The disk is wiped on every restart. That's why documents go to Supabase Storage and nothing important is stored locally.
* There is no background worker, so GitHub sync runs when you press **Sync now**, when you open the dashboard and data is older than 30 minutes, and from the scheduled workflow below.
* Render's free plan blocks outgoing email, and the app doesn't send any.

## 5. Scheduled GitHub sync (recommended)

In your GitHub repository: *Settings → Secrets and variables → Actions → New repository secret*:

* `APP_URL` = `https://<your-service>.onrender.com`
* `INTERNAL_SYNC_SECRET` = the same value as on Render

The workflow `.github/workflows/scheduled-sync.yml` then runs every 4 hours: it wakes the service, calls `POST /api/v1/internal/sync`, and prints how many sync jobs ran. You can also start it by hand from the *Actions* tab.

## 6. Weekly encrypted backups (recommended)

1. Install [age](https://github.com/FiloSottile/age) on your computer and run `age-keygen -o projectos-backup-key.txt`. **Keep this file safe and off GitHub**; it is the only way to decrypt your backups.
2. Add repository secrets:
   * `BACKUP_AGE_RECIPIENT` = the public key printed by `age-keygen` (starts with `age1…`)
   * `BACKUP_DATABASE_URL` = the Supabase session pooler string
3. `.github/workflows/backup.yml` runs every Sunday and stores `projectos-<date>.dump.age` as a private workflow artifact for 90 days. Run it once by hand to check it works. Restoring is described in [OPERATIONS.md](OPERATIONS.md#restore-a-backup).

Also use **Settings → Download everything (JSON)** in the app now and then, to keep a copy on your own computer.

## 7. First steps in the app

1. **Import register**: upload your `.xlsx`, review the preview and suggested sub-project links, then import.
2. **GitHub**: click *Load my repositories*. Repositories that a project already links to (e.g. Meza Order → `restaurant`) are linked and switched to sync automatically. Link others with the project selector and tick *Sync*.
3. **GitHub → Load my boards**: pick the start/end date fields for each Projects board and tick *Sync*.
4. Press **Sync now**, then open **Timeline**.
